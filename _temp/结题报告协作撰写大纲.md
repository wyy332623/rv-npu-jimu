### 1.3 固件与功能模拟器机制

#### 核心论点

## 2. 原项目情况的不足：从 752B 到 736B 的关键突破及其代价

### 2.1 为什么 752B→736B 是观察旧闭环问题的关键窗口

#### 核心论点

从较高流量降到 752B 仍可能来自删除明显冗余传输；从 752B 进一步压到理论下限 736B，只剩 16B 的指标空间，因此 Agent 更容易为满足单一目标而引入额外的片上搬运、控制指令或串行依赖。这个阶段最能观察“目标达成”和“工程收益”是否一致。

#### 建议材料组织

1. 先给出 752B 与 736B 两个候选的共同正确性门禁结果；
2. 展示仅与最后 16B 有关的最小源码 diff，不要粘贴整份固件；
3. 将删除的 DRAM 操作与新增的 VRF/MRF/pipe/控制操作逐项配对；
4. 区分“goal1 评分看到的收益”和“真实硬件可能付出的代价”；
5. 说明这不是简单指责 Agent，而是目标函数和提示约束共同决定的理性行为：Agent 会优化系统实际奖励的东西。

### 2.3 不足一：优化目标过于单一，后期行为偏离初衷

#### 核心论点

原 goal1 将“减少 DRAM 流量”近似为“提高 NPU 性能”。在优化初期这一代理指标通常有效，但接近下限后，删除少量 DRAM 流量可能需要更多片上搬运、控制或更长依赖链。闭环仍会奖励这种修改，于是搜索从“提升端到端性能”逐渐偏移为“满足指标定义”。

#### 需要避免的表述

- 不写成“Agent 故意作弊”；应写成“Agent 对设定奖励做了目标一致但工程上未必合理的优化”。
- 不凭主观判断说代码更慢；应列出新增命令、资源占用或后续 RTL 复测证据。

### 2.4 不足二：优化指标与真实性能之间存在明显差距

#### 核心论点

DRAM 字节数、访存次数和指令数都属于工作量指标，它们缺少发生时间和资源上下文：一次 DRAM 访问可能位于关键路径，也可能被计算完全隐藏；一次片上访问虽然字节代价小，却可能竞争最繁忙的 Vector 控制器。因此相同的字节减少量可以对应正收益、零收益或负收益。

#### 建议用一个概念式收束

```text
端到端时间变化
  ≠ 删除的 DRAM 字节 × 固定代价

端到端时间变化
  = 工作量变化
  - 新增/损失的并行隐藏
  + 依赖、控制器、总线和 bank 竞争变化
```

### 2.5 从问题到方案的过渡

本节最后提出第三节的设计需求：新的评价后端既要保留功能模拟的速度，又必须知道“命令何时执行、能否重叠、被什么资源阻塞、最后何时完成”。这自然引出混合粒度并行时序模拟器。

## 3. 暑期实践改进：支持并行调度的 NPU RTL 时序模拟器

### 3.1 设计目标与取舍

#### 核心论点

全 RTL 级模拟可以提供较高精度，但将 RISC-V、NPU 控制和完整数值数据通路全部放入逐周期仿真，会使每一轮 Agent 候选验证过慢。项目因此采用分层协同建模：对决定并行关系的控制模块使用可综合 SystemVerilog RTL，对数值功能模块继续使用快速 Python/C 模型，并通过版本化延迟契约连接二者。

#### 需要明确的两类建模

| 层次 | 建模方式 | 负责内容 | 不负责内容 |
|---|---|---|---|
| 控制/资源层 | SystemVerilog + Verilator，逐周期 | ROB、发射、依赖、五类控制器、DRAM、bank、II、栅栏、计数器 | FP16 逐位算术结果 |
| 功能/数值层 | MiniRV64 + Python 设备 + C 内核 | 指令语义、寄存器/内存状态、BERT 数值结果和 trace | RTL 资源并行的最终周期 |
| 适配层 | Python trace encoder + C++ harness | 指令分类、latency/II、资源掩码、bank 掩码、轨迹回放、产物整合 | 自行决定调度结果 |

### 3.3 控制模块的 RTL 建模

#### 建议内容

- 默认 16 项有限 ROB，命令按程序顺序进入，前端每周期最多接收一条；
- 调度器每周期最多发射一条最老的 eligible 命令；
- 同一控制器的命令保持顺序，不同控制器之间允许越过阻塞命令；
- 五类控制器为 Load、Store、MVU、Vector、Control，命令可在不同控制器上并行执行；
- 128 位语义 scoreboard 对更老未完成命令检查 RAW、WAR 和 WAW；
- `pipe`、`vpipe_a` 使用 SSA 弹性 token，物理 VRF/MRF/SRF/配置寄存器和 DRAM 区间保持真实资源身份；
- `INST_ISSUE` 在当前配置下作为保守完整 fence；
- RTL 提供周期、重叠、前端满、依赖、II、DRAM、bank、barrier、dispatch、completion、max inflight 和各控制器 busy 等计数器。

### 3.4 功能模块与指令用时的建模方式

#### 核心论点

算术功能不在 RTL 内逐位重算，而是由功能模拟器保证结果；RTL 只接收每条动态命令的延迟和启动间隔。这样避免完整数据通路 RTL 的仿真成本，同时保留了对流水线并发的必要约束。

#### 延迟来源应分三类说明

1. **显式指令契约**：例如 Vector 加减乘、Softmax、LayerNorm、归约和广播；
2. **HDL 推导公式**：例如 MVU 发射/加法树/完成返回，以及 `M_RD@18` 的 VecToMat 排空；
3. **存储层次公式**：外部 DRAM 与片上 VRF/SRF 采用不同 setup、带宽、元素宽度和最小 burst。

建议给出公式：

```text
dram_cycles = setup
            + ceil(max(payload_bytes, minimum_burst_bytes)
                   / dram_bytes_per_cycle)

on_chip_cycles = setup
               + ceil(payload_bytes / on_chip_bytes_per_cycle)
```

正文可列 dim4 的少量代表值说明量级差异，但完整参数表放附录或引用 `docs/hdl-derived-timing-parameters.md`，避免本节被参数淹没。

### 3.5 固件总执行耗时的计算机制

#### 核心论点

固件总耗时不是所有指令延迟之和，而是 RTL 根据依赖和资源约束生成时间区间后，取最后一条命令的完成周期。

#### 必须给出的指标关系

记每条命令执行区间为 `[start_i, finish_i)`：

```text
T = max(finish_i)                         # RTL makespan，闭环主评分
S = sum(finish_i - start_i)               # 串行命令周期和
U = union_length(all active intervals)    # 至少一条命令活动的周期并集

gross_overlap_cycles = S - U
scheduler_idle_hole_cycles = T - U
net_parallelism_savings_cycles = S - T
                               = gross_overlap_cycles
                               - scheduler_idle_hole_cycles
```

同时解释：

- `memory_compute_overlap_cycles` 是 DRAM 与 MVU/Vector 活动区间的真实交集；
- 各控制器 utilization 为 busy 周期并集除以 `T`；
- stall 只对当前最老阻塞命令按优先级归因，同周期仍可能发射年轻独立命令，因此 stall 不能相加成总周期；
- `rtl_idle_cycles` 还包含很短的顺序退休尾部，评分使用最后操作完成的 `T`。

### 3.6 并行过程中的竞争资源及实现

| 竞争或约束 | 实现方法 | 可能产生的结果 |
|---|---|---|
| RAW/WAR/WAW | 语义资源 read/write mask 与更老 ROB 项比较 | dependency stall |
| 同控制器顺序 | 更老未发射同 unit 命令阻止年轻命令 | order/barrier 类等待 |
| 流水线启动间隔 | `unit_next_issue` 与命令 II 比较 | unit stall |
| 共享 DRAM 总线 | DRAM 命令在整个建模传输期互斥 | dram stall |
| SRAM bank 端口 | 活动命令 bank read/write mask 冲突检测 | bank stall |
| 有限 ROB | `rob_count == ROB_DEPTH` 时关闭 `cmd_ready` | frontend-full stall |
| chain fence | barrier 必须到退休队首，年轻命令不能越过 | barrier stall |

### 4.3 结合候选固件代码说明瓶颈迁移

#### 建议选取的代码区域

- `compute_k_all_positions()`：从 `V_WR_DRAM` 改为 `V_RD + V_WR` 写入 `MEM_MFU_INITIAL_VRF`；
- `compute_v_all_positions()`：相同的 DRAM→VRF 替换；

#### 因果链

```text

        ↓
增加/保留 Vector 控制器上的 V_RD/V_WR 搬运
        ↓
```

## 5. 闭环工作流对并行模拟器的适配：让 Agent 理解并行证据

### 5.1 从 `rtl-dram-optimization` 到 `rtl-dram-exploration`

#### 核心论点

前者只允许复刻旧 K/V 缓存策略，目的是审计旧 skill；后者允许 Agent 在每轮读取当前最佳调度，依次选择新的、位于关键因果链附近的 DRAM 数据放置机会。变化不只是把评分字段改成 cycles，而是让 Agent 的观察、推理、修改约束和反馈全部围绕并行调度重新组织。

#### Goal 对比表

| 维度 | `rtl-dram-optimization` | `rtl-dram-exploration` |
|---|---|---|
| 任务性质 | 复审固定历史 K/V 变换 | 连续探索尚未实现的 DRAM/片上数据放置 |
| 每轮假设 | 只允许 K/V 缓存 | 一个新的 causal DRAM 机会 |
| 主评分 | RTL makespan | RTL makespan |
| DRAM 字节 | 诊断 | 诊断，不足以晋升 |
| Agent 证据 | 调度用于解释固定变换 | 当前最佳的关键链、依赖、资源、利用率和历史反馈 |
| 已实现机会处理 | 无关 | 不得重复，继续寻找 Q、scratch、常量、残差等机会 |

### 5.2 为并行优化增加的 Agent 证据

#### 应说明的适配工作

- 将 `timing-schedule.json` 的完整路径和 profile 指纹写入 prompt；
- 提供当前 makespan、串行工作量、gross overlap、调度空洞、存储/计算重叠和控制器利用率；
- 提供事后因果链中的最长事件和最大等待，而不是只给全局访存聚类；
- 提供 `dependency_predecessors`、RAW/WAR/WAW 原因和具体 `dependency_resources`；
- 提供 DRAM logical payload 与最小 burst 后 transaction bytes，避免只看裸元素数；
- 提醒 Agent stall 是非可加压力，动态 command ID 不是源码行号；
- 将 tensor、命令、时序和 DWARF 来源合并为 cross-layer graph；
- 保留完整事件数组作为审计文件，prompt 只放有界摘要。

### 5.3 为可靠闭环增加的执行约束

- Agent 每轮只实现一个主要假设，使实测变化可归因；
- Agent 只做一次快速自检，正式 build、probe 和正确性门禁由闭环统一执行；
- RTL、profile、模拟器、指标、测试和产物都不允许 Agent 修改；
- 每个候选都与固定运行基线评分，并和当前最佳比较后决定晋升；
- 未改动、Agent 超时、门禁失败、性能未提升分别记录；
- 下一轮收到最近失败候选的指标增量，避免重复资源迁移；
- 工作树始终可以恢复，最佳候选单独存档。

## 6. 大参数固件优化：验证流程具有一定规模普适性

### 6.1 为什么需要大参数实验

#### 核心论点

小配置中的地址、容量和循环结构可能让某些优化偶然成立。将工作负载扩展到 `NATIVE_DIM=16、hidden_size=16、seq_len=16`，可以检验布局、构建、trace、RTL 回放、Agent 提示、门禁和候选晋升是否仍能组成完整闭环。

注意本节证明的是**对更大参数规模具有一定适应性**，不是已经证明对任意模型、任意固件都普适。

### 6.2 大配置工程适配

#### 建议内容

- 输入张量为 `16×16=256` elements，是历史 dim4/seq6 的 24 elements 的 10.67 倍；
- 六个投影/FFN 参数矩阵为 `16×16`；
- 使用 `packed-v2` 布局计算器统一固件、工作负载、测试和 probe 的地址；
- dim16 profile 使用 16 个 MVU/Vector lane、8B/cycle 外部 DRAM 和 32B/cycle 片上带宽；
- 单头是当前向量 mask 语义限制下的有意选择；
- 该 profile 由控制器公式外推，适合相对比较，未用 dim16 硬件校准。

### 6.3 `rtl-cycle-optimization-large` 的 Agent 策略

- 唯一晋升指标为 `rtl_predicted_npu_cycles`；
- 每轮只改一个主要假设；
- 不允许硬编码 `packed-v2` 地址；
- 除 dim16 正确性外，额外执行 legacy dim4 回归；
- 从关键因果链、tensor 语义、依赖和资源利用率选择权重驻留、scratch 消除、片上缓存或软件流水机会。

## 7. 项目不足与未来发展方向

### 7.1 不足一：固件正确性门禁仍不等同于真实硬件正确性

#### 现状

当前数值结果主要由 Python/C 功能模拟器和有限的可观察张量门禁保证。`run-20260817-162615-1077` 中 K/V 地址重叠曾被最终输出的 FP16 量化掩盖，说明只检查最终结果可能漏掉中间语义错误。时序 RTL 又不含完整算术数据通路，因此“功能测试通过 + 时序模型更快”仍不能完全代表真实硬件正确执行。

#### 未来方向

- 在真实 FPGA/NPU 硬件上执行候选并比对结果；
- 提供配套的完整 RTL 或参考 HDL 数据通路仿真作为高等级正确性 oracle；
- 增加 Q/K/V、Attention score、Softmax probability、context、LayerNorm 等中间张量门禁；
- 使用多个随机种子、更多维度和边界输入，避免量化偶然掩盖错误；
- 将功能模型、命令/控制 RTL、完整 RTL/真实硬件组织成分级验证阶梯。

### 7.2 不足二：优化对象集中于 `bert_layer.c`，任务普适性尚未充分验证

#### 现状

现有成功案例基本围绕 BERT encoder layer，同一批优化假设集中在投影权重、Q/K/V、Attention scratch、LayerNorm 和 FFN 数据流。大参数实验验证了规模扩展，但没有验证不同网络结构、不同固件控制模式或多 kernel 协同。

#### 未来方向

- 增加 CNN、MLP、RNN、稀疏算子或其他 Transformer 变体；
- 使用 workload manifest 描述不同 ELF、tensor、observables 和硬件配置；
- 将 skill 从 BERT 专用经验抽象为通用的生命周期、驻留、双缓冲、bank 分配和软件流水规则；
- 通过跨工作负载重复实验，统计命中率、错误率、平均提升和迁移失败原因；
- 逐步允许 Agent 在受控范围内联合修改多个 kernel，而不是只优化单个 `bert_layer.c`。

### 7.3 不足三：时序参数尚未硬件校准，模型排名的外推可信度有限

#### 现状

当前 MVU、Vector、VecToMat、DRAM setup/带宽和片上带宽采用 HDL 推导的一阶契约或显式假设。它们可以在同一 profile 下稳定比较候选，但尚未通过目标 FPGA/ASIC 的组件级 microbenchmark、总线波形或综合后时序全面校准。不同 profile 可能改变瓶颈和候选排序。

#### 未来方向

- 在真实 HDL/RTL 上测量 command accept、result valid、next accept 和流水线重叠；
- 用 FPGA 性能计数器标定 DRAM setup、burst、bank 冲突和控制器 II；
- 保存 profile 版本、SHA-256、硬件版本和测量误差，形成可复现实验契约；
- 对关键候选进行多 profile 灵敏度分析，优先接受在合理参数区间内排序稳定的优化；
- 将面积、功耗、频率和资源占用引入评分，扩展为软硬件联合多目标搜索。

### 7.4 总结与展望

#### 建议结论逻辑

1. 原项目证明了 Agent 能在严格门禁下将明确指标优化到理论下限；
2. 极限阶段和 RTL 负优化案例证明，代理指标设置会决定 Agent 的行为边界；
3. 混合粒度并行模拟器以可接受速度补充了依赖、资源竞争和真实重叠；
4. 并行感知的提示、skill、门禁和评分使 Agent 能从“减少字节”转向“缩短完成时间”；
5. 小参数探索和大参数闭环说明方法有效并具有一定规模适应性；
6. 后续必须通过更强正确性 oracle、更多工作负载和硬件标定，才能从研究原型走向可信的软硬件联合优化系统。

最后一句建议落在方法论上：**智能体优化的上限不仅取决于模型能力，更取决于反馈是否真实、目标是否完整以及验证是否足够严格。**
