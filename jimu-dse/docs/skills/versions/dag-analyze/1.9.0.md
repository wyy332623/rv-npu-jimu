# DAG Analyze Skill

## Inputs

Use the exact run-specific paths in the prompt and attached files. Closed-loop
runs place DAG data under `jimu-dse/results/<run>/dag_agent/`; never assume the
legacy `_out/` path.

### Closed-loop fast path

When `next_macro_contract.json` is attached, it is authoritative. Read only the
contract, the target firmware, the mandatory skills, and the supplied metric
probe. Do not reopen the full DAG, inspect framework/gate source, regenerate
evidence, select another macro, or repeat a proof whose digest is recorded in
the contract. Implement its exact marker, source invariants, bank/region plan,
and Tensor/address scope. If its status is not `ready`, leave firmware
unchanged.

The artifact table and manual workflow below are fallback procedures for
diagnosis outside a contract-driven closed-loop turn.

Read artifacts in this order:

| Priority | File | Content |
|---:|---|---|
| 1 | `multiseq_summary.md` | Measured seq2/seq6 reuse families and implementation readiness |
| 2 | `macro_candidate_summary.md` | Ranked L1/L2/L3 macros and cross-config status |
| 3 | `allocation_summary.md` | Compact matrix, proof digests and reference allocation regions |
| 4 | `allocation_proof.json` | Full allocation for every required dim/hidden/seq configuration; open after selection |
| 5 | `loop_invariants.json` | Cross-sequence counts, values, addresses and allocation status |
| 6 | `candidate_evidence.jsonl` | Compact macro/candidate records and representative nodes |
| 7 | `macro_candidates.json` | Full macro scope, exact Tensor/address members and proof digests |
| 8 | `candidate_summary.md` | Ranked primitive L1 round trips and VRF plan status |
| 9 | `candidates.json` | Full primitive proof, rejected pairs and analysis limits |
| 10 | `lifetimes.json` | Existing VRF definition-use intervals and next definitions |
| 11 | `summary.md` | Configuration, phases, repeated patterns and low-AI phases |
| 12 | `phases.json` | Stable phase IDs, members, Tensor inputs/outputs, traffic and FLOPs |
| 13 | `tensors.json` | Tensor slices with producer and consumer node IDs |
| 14 | `patterns.json` | Compressed repeated phase instances |
| 15 | `micro_ops.jsonl` | Every micro-op with stable ID, defs/uses and semantic annotations |
| 16 | `edges.jsonl` | Producer-consumer dependencies with stable node IDs |

`run_metadata.json` records the schema version, firmware configuration, ELF
SHA256, counts and annotation method. Check it before comparing runs.
The root DAG is the concrete seq6 reference; `seq2/` is the concrete short
sequence DAG. `multiseq_metadata.json` binds both inputs and their ELF hashes.

## Evidence Rules

- Stable IDs such as `op-000033` and `phase-0007` are the preferred references.
- Raw `uses`, `defs`, event indices and dependency edges are authoritative.
- Tensor, phase, position and tile annotations are heuristic. Cross-check them
  against raw resources and firmware address macros before editing.
- `head` is currently unavailable and must not be inferred without source proof.
- Compare DAGs only when firmware configuration and ELF identity are recorded.
- PR3 checks exact DRAM addresses, not partially overlapping address ranges.
- A `reuse` candidate proves only that its source VRF resource is not redefined
  before the last consumer. A `relocate` candidate has no proven allocation.
- PR3 `projected_seq*` values are estimates; independent probes are
  authoritative. DAG-PR5 `measured_removable_read_bytes` values come from the
  two concrete traces but remain opportunity bounds, not accepted savings.
- Accept a macro only when `eligible`, `allocation_proven`,
  `cross_config_proven`, and `validation_matrix_complete` are all true.
- DAG-PR5 aligns graphs by Tensor+tile semantics because addresses move with
  sequence layout. It retains exact per-configuration addresses and slices.
- DAG-PR6 proves L1/L2 capacity, alignment and non-overlap against every
  observed VRF lifetime in the required validation matrix. Follow its exact
  named bank, offset and lifetime plan; do not invent a replacement region.
- Accept L3 only when its generated macro is `implementation_ready=true`.
  The deterministic K/V and Q contracts prove position interchange, one-tile
  MRF residency, distinct bank-13 partial sums, and unchanged per-output `tc`
  order across all six configurations. Q additionally proves a disjoint
  bank-13 output region because attention rebuilds and clobbers MRF. Other L3
  phases remain blocked until they receive their own phase-level contract.

## Analysis Workflow

Skip this workflow when the closed-loop fast path supplied a ready contract.

### 1. Read the multi-sequence opportunity map

Read `multiseq_summary.md`, then confirm the top entries in
`loop_invariants.json`. Distinguish these families:

- L1: produced intermediates retained instead of DRAM round trips;
- L2: repeated read-only inputs, biases, LayerNorm values or unit vectors;
- L3: weight tiles repeatedly loaded across sequence positions.

Use seq2 and seq6 read counts to reject seq1-only intuitions. Treat removable
bytes as an upper bound: compulsory first loads, VRF pressure and schedule
changes still apply. Use `candidate_evidence.jsonl` for the compact proof and
open full files in the run directory only when a representative node is
insufficient.

### 2. Select one implementation scope

Start with `macro_candidate_summary.md`. Select exactly one eligible macro at
the lowest unfinished level. Several members of one macro are one coherent
change; never combine L1 with L2 or L3 in one iteration.

Select L2 only when no eligible L1 macro remains. Select L3 only when no
eligible L1/L2 macro remains and L3 itself is implementation-ready. The
independent gate enforces this order.

If no macro is eligible or its all-configuration source proof fails, fall back
to exactly one eligible primitive from `candidate_summary.md`. Prefer high
expected seq6 savings, but account for confidence and VRF plan:

- `eligible-reuse-source-vrf`: source reuse is structurally proven.
- `eligible-requires-vrf-relocation`: do not edit until a new allocation is
  proven from `lifetimes.json` and firmware source.

Never select an entry from `rejected`, a macro with an incomplete validation
matrix, or any record with `implementation_ready=false`.

### 3. Confirm its phase

Use the low arithmetic-intensity table in `summary.md` and confirm the selected
candidate's phase in `phases.json`:

```text
AI = compute_flops / (dram_load_bytes + dram_store_bytes)
```

Low-AI, high-traffic phases are the primary memory-optimization targets.
Repeated patterns can multiply the benefit across positions or tiles.

### 4. Confirm its Tensor slice

Use `tensors.json` to find DRAM Tensor slices with both producers and consumers.
Follow the stable node IDs into `micro_ops.jsonl`.

### 5. Verify the generated save-load proof

A save-load pair is a `DRAM_STORE` followed by a `DRAM_LOAD` of the same DRAM
address, with no intervening write to that address. Confirm the producer edge
in `edges.jsonl` or `micro_op_dag.txt`.

Example:

```text
op-000033 DRAM_STORE defs=DRAM[0x300]
op-000150 DRAM_LOAD  uses=DRAM[0x300]
edge: op-000033 -> op-000150 via DRAM[0x300]
```

This is a candidate for replacing:

```text
VRF -> DRAM -> VRF
```

with:

```text
VRF -> retained VRF value -> consumer
```

### 6. Map evidence to firmware

1. Use the node event indices to narrow the execution location.
2. Use Tensor and address annotations to find the corresponding firmware macro.
3. Find the producer and all consumers in `firmware/bert/bert_layer.c`.
4. Verify position/tile addressing from source; do not rely only on annotations.

### 7. Produce a VRF lifetime proof

Before editing, state one row per macro member (or for the primitive fallback):

```text
Selected phase ID:
Selected candidate ID:
Selected macro ID:
Selected Tensor slice:
Producer node:
Consumer nodes:
DRAM address:
Intervening write:
VRF allocation:
Lifetime:
Conflicts:
PR3 VRF status:
Allocation proven:
Expected seq2 saving:
Expected seq6 saving:
```

For a macro in manual fallback mode, reproduce the exact reference allocation
table and cite every configuration proof digest from
`allocation_proof.json`. For a `relocate` primitive, inspect every
overlapping lifetime and prove the
chosen bank/row is not defined or live anywhere in the extended interval.
Reject the transformation yourself if an intervening write exists, allocation
is unproven, the VRF range conflicts, or a consumer cannot use the cached layout.

## Required Output

Produce a list of eligible pairs using stable IDs:

```text
Save-load pairs:
  candidate-dram-0007:
  K[pos=0,tile=0]:
    op-000033 DRAM_STORE -> op-000150 DRAM_LOAD
    address=0x300, phase=phase-0007, intervening_write=no
```

Then provide the lifetime and allocation proof before modifying firmware.

## PR4 candidate declaration and acceptance

For a `total_bytes` optimization, prefer exactly one macro declaration:

```c
// JIMU_DAG_MACRO: macro-dram-l1-attention
```

An eligible L2 iteration uses its current macro ID, for example:

```c
// JIMU_DAG_MACRO: macro-dram-l2-loop-invariants
```

Only when no eligible macro can be proved, declare one primitive fallback:

```c
// JIMU_DAG_CANDIDATE: candidate-dram-0007
```

The ID must come from the current iteration's matching JSON file. Replace all
older DAG markers instead of adding another. Never declare both marker types,
a rejected/blocked ID, an ID from an earlier iteration, or more than one ID.

After correctness and metric validation, the independent PR4 gate writes:

- `dag_diff_N.json`: declaration, selected Tensor delta, micro-op delta,
  measured seq2/seq6 traffic, PR3 estimate and gate reasons;
- `dag_diff_N.md`: compact human-readable evidence report.

The gate requires all of the following for G1:

1. exactly one valid macro or primitive declaration with a complete
   cross-configuration allocation proof;
2. for a macro, a reduction at every declared Tensor/address resource and no
   positive DRAM reduction outside its strict scope; for a primitive, a
   reduction in DRAM operations for its declared Tensor slice;
3. no measured seq2 DRAM regression;
4. a strict measured seq6 DRAM improvement.
5. no eligible lower-level macro remains when L2 or L3 is selected.

Measured traffic and the structural DAG direction are authoritative. A large
difference from the PR3 heuristic is reported for investigation but is not by
itself a rejection.
