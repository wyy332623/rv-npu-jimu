# DAG Analyze Skill

## Inputs

Use the exact run-specific paths in the prompt and attached files. Closed-loop
runs place DAG data under `jimu-dse/results/<run>/dag_agent/`; never assume the
legacy `_out/` path.

Read artifacts in this order:

| Priority | File | Content |
|---:|---|---|
| 1 | `candidate_summary.md` | Ranked eligible DRAM round trips, estimated savings and VRF plan status |
| 2 | `candidates.json` | Candidate proof, rejected pairs, overwrite checks and analysis limits |
| 3 | `lifetimes.json` | Existing VRF definition-use intervals and next definitions |
| 4 | `summary.md` | Configuration, phases, repeated patterns, low-AI phases and candidate table |
| 5 | `phases.json` | Stable phase IDs, members, Tensor inputs/outputs, traffic and FLOPs |
| 6 | `tensors.json` | Tensor slices with producer and consumer node IDs |
| 7 | `patterns.json` | Compressed repeated phase instances |
| 8 | `micro_ops.jsonl` | Every micro-op with stable ID, defs/uses and semantic annotations |
| 9 | `edges.jsonl` | Producer-consumer dependencies with stable node IDs |
| 10 | `micro_op_dag.txt` | Legacy raw evidence for forensic cross-checking |
| 11 | `dram_clusters.txt` | Legacy DRAM-flow cluster table |

`run_metadata.json` records the schema version, firmware configuration, ELF
SHA256, counts and annotation method. Check it before comparing runs.

## Evidence Rules

- Stable IDs such as `op-000033` and `phase-0007` are the preferred references.
- Raw `uses`, `defs`, event indices and dependency edges are authoritative.
- Tensor, phase, position and tile annotations are heuristic. Cross-check them
  against raw resources and firmware address macros before editing.
- `head` is currently unavailable and must not be inferred without source proof.
- Compare DAGs only when firmware configuration and ELF identity are recorded.
- PR3 checks exact DRAM addresses, not partially overlapping address ranges.
- A `reuse` candidate proves only that its source VRF resource is not redefined
  before the last consumer. A `relocate` candidate has no proven allocation.
- seq2/seq6 savings are estimates; independent probes are authoritative.

## Analysis Workflow

### 1. Select a ranked candidate

Start with `candidate_summary.md`. Select exactly one eligible candidate ID.
Prefer high expected seq6 savings, but account for confidence and VRF plan:

- `eligible-reuse-source-vrf`: source reuse is structurally proven.
- `eligible-requires-vrf-relocation`: do not edit until a new allocation is
  proven from `lifetimes.json` and firmware source.

Never select an entry from `rejected`.

### 2. Confirm its phase

Use the low arithmetic-intensity table in `summary.md` and confirm the selected
candidate's phase in `phases.json`:

```text
AI = compute_flops / (dram_load_bytes + dram_store_bytes)
```

Low-AI, high-traffic phases are the primary memory-optimization targets.
Repeated patterns can multiply the benefit across positions or tiles.

### 3. Confirm its Tensor slice

Use `tensors.json` to find DRAM Tensor slices with both producers and consumers.
Follow the stable node IDs into `micro_ops.jsonl`.

### 4. Verify the generated save-load proof

A save-load pair is a `DRAM_STORE` followed by a `DRAM_LOAD` of the same DRAM
address, with no intervening write to that address. Confirm the producer edge
in `edges.jsonl` or `micro_op_dag.txt`.

Example:

```text
op-000033 DRAM_STORE defs=DRAM[0x300]
op-000150 DRAM_LOAD  uses=DRAM[0x300]
edge: op-000033 -> op-000150 via DRAM[0x300]
```

This is a candidate for replacing:

```text
VRF -> DRAM -> VRF
```

with:

```text
VRF -> retained VRF value -> consumer
```

### 5. Map evidence to firmware

1. Use the node event indices to narrow the execution location.
2. Use Tensor and address annotations to find the corresponding firmware macro.
3. Find the producer and all consumers in `firmware/bert/bert_layer.c`.
4. Verify position/tile addressing from source; do not rely only on annotations.

### 6. Produce a VRF lifetime proof

Before editing, state:

```text
Selected phase ID:
Selected candidate ID:
Selected Tensor slice:
Producer node:
Consumer nodes:
DRAM address:
Intervening write:
VRF allocation:
Lifetime:
Conflicts:
PR3 VRF status:
Allocation proven:
Expected seq2 saving:
Expected seq6 saving:
```

For a `relocate` candidate, inspect every overlapping lifetime and prove the
chosen bank/row is not defined or live anywhere in the extended interval.
Reject the transformation yourself if an intervening write exists, allocation
is unproven, the VRF range conflicts, or a consumer cannot use the cached layout.

## Required Output

Produce a list of eligible pairs using stable IDs:

```text
Save-load pairs:
  candidate-dram-0007:
  K[pos=0,tile=0]:
    op-000033 DRAM_STORE -> op-000150 DRAM_LOAD
    address=0x300, phase=phase-0007, intervening_write=no
```

Then provide the lifetime and allocation proof before modifying firmware.
